# 同行旅 V3.0 需求文档：地图行程与预算管理升级

## 0. 版本定位

V3.0 是一次较大的功能更新，目标是把「同行旅」从基础的多人旅行记录工具，升级为更接近真实出行场景的协作型旅行管理工具。

本版本核心升级方向：

1. 接入地图选址能力，提高行程地点录入准确性。
2. 提供每日行程地图全览，展示路线、距离、预计耗时。
3. 优化行程展示结构，包括行程序号、卡片布局、时间线视图。
4. 增强行程状态感知，包括当前行程高亮、已结束变灰、冲突提示。
5. 将账单模块从“记账”升级为“预算管理”，支持总预算、分类预算、人均预算消耗和超预算提醒。

------

# 2. 地图接口接入

## 2.1 功能目标

在行程管理中，每次添加或编辑地点时，不再只允许用户手动输入地点名称，而是呼出地图选址界面，让用户在地图上搜索、选择、确认地点。

这样可以解决以下问题：

1. 地点名称不规范。
2. 同名地点歧义。
3. 后续无法进行路线规划。
4. 行程全览缺少经纬度数据。
5. 用户手动输入地址容易出错。

------

## 2.2 技术方向

微信小程序可使用微信原生地图能力，优先考虑以下接口：

```javascript
wx.chooseLocation()
wx.openLocation()
```

如后续需要更复杂的路线规划、距离计算、POI 搜索，可接入腾讯位置服务相关能力。

本版本最低要求：

1. 添加行程时可以通过地图选择地点。
2. 保存地点名称、地址、经纬度。
3. 行程详情中可以打开地图查看地点。
4. 行程全览可以使用经纬度进行路线展示或路线规划。

------

## 2.3 添加行程时的交互流程

### 原流程

用户手动输入：

```text
标题
地点
开始时间
结束时间
备注
```

### V3.0 新流程

用户填写：

```text
标题
地点：点击选择地点
开始时间
结束时间
备注
```

点击“选择地点”后：

1. 调用地图选址界面。
2. 用户在地图中搜索或拖动选择地点。
3. 用户点击确认。
4. 页面自动回填：
   - 地点名称
   - 详细地址
   - 纬度 latitude
   - 经度 longitude
5. 用户可以继续编辑标题、时间和备注。
6. 点击保存后，将地点信息一起写入数据库。

------

## 2.4 地点字段展示要求

添加或编辑行程页中，地点区域应展示为：

```text
地点
[ 北京首都国际机场 T3航站楼        > ]
北京市朝阳区机场南路
```

如果用户尚未选择地点，则显示：

```text
地点
[ 点击选择地图地点                  > ]
```

地点选择后应支持重新选择。

------

## 2.5 数据结构调整

行程 item 需要新增地点相关字段。

### trips/{tripId}/schedules/{scheduleId}

建议结构：

```javascript
{
  _id: "scheduleId",
  tripId: "tripId",

  title: "机场集合",
  note: "提前办理值机",
  
  startTime: Date,
  endTime: Date,

  locationName: "北京首都国际机场T3航站楼",
  locationAddress: "北京市朝阳区机场南路",
  latitude: 40.0525,
  longitude: 116.6156,
  poiId: "",

  createdBy: "userOpenId",
  createdAt: Date,
  updatedAt: Date
}
```

说明：

- `locationName`：地图返回的地点名称。
- `locationAddress`：地图返回的详细地址。
- `latitude` / `longitude`：路线规划和地图展示的核心字段。
- `poiId`：如果地图接口返回 POI ID，则保存；如果没有可以为空。
- 兼容旧数据：旧行程可能没有经纬度，页面不能崩溃。

------

## 2.6 兼容旧数据要求

由于 V2 之前的行程可能只有手动地点文本，没有经纬度，因此 V3.0 必须兼容。

如果某条行程没有经纬度：

1. 普通行程列表仍正常展示。
2. 时间线视图仍正常展示。
3. 地图全览中跳过该地点，并提示：

```text
部分行程缺少地图位置，无法加入路线规划。
```

1. 编辑旧行程时，允许用户重新选择地图地点补全经纬度。

# 3. 行程地图全览

## 3.1 功能目标

在行程页提供“地图全览”能力。用户可以选择某一天，系统根据当天的行程地点顺序，在地图上展示路线、地点标记、导航距离和预计时间。

------

## 3.2 入口设计

建议在行程页顶部增加入口：

```text
[ 6月5日 ▼ ]           [ 地图全览 ]
```

或者在日期分组标题右侧增加：

```text
6月5日 周五             查看地图
```

点击后进入：

```text
pages/schedule-map/schedule-map
```

------

## 3.3 地图全览页面内容

地图全览页应包含：

1. 地图区域。
2. 当天所有有经纬度的行程地点标记。
3. 按行程顺序编号的 marker。
4. 路线 polyline。
5. 路线摘要信息：
   - 总距离
   - 预计总耗时
   - 地点数量
6. 地点列表摘要。

示例：

```text
6月5日 行程路线

总距离：18.6 km
预计时间：42 分钟
地点数：4 个

1. 09:00 机场集合
2. 14:00 到达酒店
3. 18:00 晚餐
4. 20:00 夜市
```

------

## 3.4 地图 marker 规则

同一天内行程编号从 1 开始。

地图 marker 文案：

```text
1
2
3
4
```

marker 对应行程卡片：

```text
1. 09:00 机场集合
   北京首都国际机场T3航站楼
```

要求：

1. marker 编号必须和行程列表编号一致。
2. 已结束行程可以使用弱化样式。
3. 当前进行中行程可以使用高亮样式。
4. 如果没有经纬度，不生成 marker。

------

## 3.5 路线规划规则

路线规划以同一天内的行程开始时间排序为准。

例如：

```text
09:00 A
11:00 B
14:00 C
18:00 D
```

路线为：

```text
A -> B -> C -> D
```

注意：

1. 不做自动最短路径重排。
2. 因为旅行计划应尊重用户安排顺序，而不是地图最优顺序。
3. 后续版本可以增加“智能优化路线”，但 V3.0 暂不强制。

------

## 3.6 路线规划边界条件

### 情况一：当天没有行程

显示：

```text
当天暂无行程，无法生成地图路线。
```

### 情况二：当天只有一个有效地点

显示该地点 marker，并提示：

```text
当天只有一个可定位地点，暂无路线规划。
```

### 情况三：部分地点缺少经纬度

展示可定位地点路线，并提示：

```text
有 2 个行程缺少地图位置，未加入路线规划。
```

### 情况四：地图接口失败

显示：

```text
地图路线加载失败，请稍后重试。
```

但页面不能白屏。

# 4. 行程序号

## 4.1 功能目标

在行程页中，同一日内的行程应自动编号，提升用户对每日行程顺序的理解。

------

## 4.2 编号规则

1. 按日期分组。
2. 每一天单独从 1 开始编号。
3. 同一天内按 `startTime` 升序排序。
4. 如果开始时间相同，则按创建时间排序。
5. 编号只用于展示，不需要写入数据库。

示例：

```text
6月5日

1. 09:00 机场集合
2. 11:30 飞机起飞
3. 14:00 到达酒店
4. 18:00 晚餐
```

第二天重新开始：

```text
6月6日

1. 09:00 早餐
2. 10:00 博物馆
3. 13:00 午餐
```

------

## 4.3 卡片中的编号展示

普通列表卡片建议展示为：

```text
┌────────────────────────────┐
│ ① 机场集合              09:00 │
│ 北京首都国际机场T3航站楼     │
│ 提前办理值机                 │
└────────────────────────────┘
```

或者：

```text
[1] 机场集合              09:00
    北京首都国际机场T3航站楼
    提前办理值机
```

要求：

1. 编号清晰但不要喧宾夺主。
2. 编号与地图 marker 保持一致。
3. 编号在普通列表和时间线视图中都应出现。

# 5. 行程页卡片布局优化

## 5.1 当前问题

目前行程卡片中的时间、地点、标题、备注都左对齐，导致右侧空白明显，视觉利用率较低。

------

## 5.2 优化目标

将时间信息放在卡片右侧，使卡片形成更合理的信息层级。

------

## 5.3 建议布局

### 普通卡片样式

```text
┌──────────────────────────────┐
│ ① 机场集合              09:00 │
│ 北京首都国际机场T3航站楼       │
│ 提前办理值机                   │
└──────────────────────────────┘
```

如果有开始和结束时间：

```text
┌──────────────────────────────┐
│ ① 酒店入住        14:00-15:00 │
│ 墨尔本市中心酒店               │
│ 需要提前联系前台               │
└──────────────────────────────┘
```

------

## 5.4 信息优先级

卡片内信息优先级如下：

1. 标题
2. 时间
3. 地点
4. 备注
5. 状态提示

视觉要求：

- 标题左上。
- 时间右上。
- 地点在第二行。
- 备注在第三行，颜色弱化。
- 状态标签可以放在标题下方或右侧。

------

## 5.5 卡片状态样式

根据当前时间与行程时间关系，卡片应有不同状态：

### 未开始

正常样式。

```text
即将开始
```

### 进行中

高亮样式。

```text
进行中
```

### 已结束

弱化样式。

```text
已结束
```

已结束行程要求：

1. 文字颜色变浅。
2. 卡片背景弱化。
3. 不影响点击查看和编辑。

# 6. 时间线式行程视图

## 6.1 功能目标

除了普通列表，行程页新增时间线式视图，更适合查看一天内按时间推进的旅行安排。

------

## 6.2 视图切换

行程页顶部增加视图切换：

```text
[ 列表 ] [ 时间线 ]
```

或者：

```text
行程视图：列表 / 时间线
```

推荐使用 segmented control 样式。

------

## 6.3 时间线展示结构

示例：

```text
6月5日

09:00  ① 机场集合
       北京首都国际机场T3航站楼

11:30  ② 飞机起飞
       北京首都国际机场

14:00  ③ 到达酒店
       墨尔本市中心酒店

18:00  ④ 晚餐
       Chinatown
```

要求：

1. 按日期分组。
2. 每天内部按开始时间排序。
3. 同一天编号从 1 开始。
4. 时间在左侧。
5. 行程内容在右侧。
6. 日期标题清晰区分。
7. 支持点击某一项进入编辑或详情。

------

## 6.4 自动高亮当前时间状态

系统根据当前时间自动判断每条行程状态。

### 状态判断规则

假设当前时间为 `now`。

如果有 `startTime` 和 `endTime`：

```javascript
if (now < startTime) {
  status = "upcoming"
} else if (now >= startTime && now <= endTime) {
  status = "ongoing"
} else {
  status = "ended"
}
```

如果只有 `startTime`，没有 `endTime`：

```javascript
if (now < startTime) {
  status = "upcoming"
} else {
  status = "started"
}
```

建议尽量要求用户填写结束时间，因为结束时间会影响冲突检测和状态判断。

------

## 6.5 即将进行的行程

为了提高实用性，可以增加“即将进行”判断。

建议规则：

```text
距离开始时间小于等于 60 分钟，且尚未开始
```

显示：

```text
即将开始
```

例如：

```text
17:30 当前时间
18:00 晚餐
```

该行程显示为“即将开始”。

------

## 6.6 已结束行程变灰

已结束行程在时间线中应弱化展示。

要求：

1. 时间文字变浅。
2. 标题文字变浅。
3. 时间线节点颜色变浅。
4. 仍然可以点击查看详情。

# 7. 行程冲突提示

## 7.1 功能目标

当同一天内多个行程时间重叠时，系统应提示用户存在行程冲突。

例如：

```text
10:00-12:00 博物馆
11:30-13:00 午餐
```

这两个行程存在时间冲突。

------

## 7.2 冲突检测规则

只检测同一天内的行程。

两个行程 A 和 B 如果满足：

```javascript
A.startTime < B.endTime && B.startTime < A.endTime
```

则认为冲突。

前提：

1. 两个行程都必须有开始时间。
2. 两个行程都必须有结束时间。
3. 没有结束时间的行程暂不参与严格冲突检测。

------

## 7.3 冲突提示位置

### 行程列表页

在冲突行程卡片上显示：

```text
时间冲突
```

例如：

```text
① 博物馆              10:00-12:00
   时间冲突：与 ② 午餐 重叠
```

### 添加/编辑行程页

保存时检测冲突。

如果发现冲突，不强制禁止保存，但应弹窗提醒：

```text
该行程与「午餐」时间重叠，是否仍然保存？
```

按钮：

```text
取消
仍然保存
```

原因：旅行中可能存在部分成员分头行动，不能一刀切禁止冲突。

------

## 7.4 冲突展示要求

1. 冲突提示不能过于刺眼。
2. 应明确说明与哪一项冲突。
3. 如果同时与多项冲突，显示前 2 项，剩余用“等”概括。

示例：

```text
与「午餐」「酒店入住」等行程时间重叠
```

------

# 8. 预算管理

## 8.1 功能目标

将账单模块从“记账”升级为“预算管理”。

原有账单功能继续保留：

1. 添加支出。
2. 添加退款或入账。
3. 分类。
4. 付款人。
5. 参与人。
6. AA 结算。
7. 编辑/删除权限控制。

V3.0 新增预算能力：

1. 设置总预算。
2. 设置分类预算。
3. 显示已花费比例。
4. 超预算提醒。
5. 人均预算消耗。
6. 分类预算消耗进度。

------

## 8.2 预算入口设计

账单页顶部增加预算总览卡片：

```text
当前总花费 ¥3,250 / 预算 ¥4,000
已使用 81.25%
人均已花费 ¥812.50
```

如果超过预算：

```text
当前总花费 ¥4,320 / 预算 ¥4,000
已使用 108.00%
已超预算 ¥320
```

------

## 8.3 预算设置入口

在账单页增加按钮：

```text
预算设置
```

进入：

```text
pages/budget-setting/budget-setting
```

预算设置页包含：

```text
总预算
[ 4000.00 ]

分类预算
餐饮     [ 1200.00 ]
交通     [ 800.00 ]
住宿     [ 1500.00 ]
门票     [ 300.00 ]
购物     [ 200.00 ]
其他     [ 0.00 ]

[ 保存 ]
```

------

## 8.4 预算分类

分类保持与账单分类一致：

```text
餐饮
交通
住宿
门票
购物
其他
```

要求：

1. 账单分类和预算分类必须统一。
2. 选择“其他”时，如果之前已经支持用户自定义备注，则预算统计仍归入“其他”大类。
3. 分类预算可以不填。
4. 如果分类预算不填，则该分类只显示已花费，不显示超预算。

------

## 8.5 预算数据结构

建议在 trip 文档下新增 `budget` 字段。

### trips/{tripId}

```javascript
{
  _id: "tripId",
  name: "日本旅行",
  creatorId: "userOpenId",

  budget: {
    totalBudget: 4000,
    categoryBudgets: {
      food: 1200,
      transport: 800,
      hotel: 1500,
      ticket: 300,
      shopping: 200,
      other: 0
    },
    updatedAt: Date,
    updatedBy: "userOpenId"
  }
}
```

分类 key 建议统一为：

```javascript
food       // 餐饮
transport  // 交通
hotel      // 住宿
ticket     // 门票
shopping   // 购物
other      // 其他
```

------

## 8.6 金额计算逻辑

账单需要区分：

```text
支出 expense
退款 refund
入账 income
```

建议账单字段：

```javascript
{
  amount: 100,
  type: "expense", // expense | refund | income
  category: "food"
}
```

预算统计时：

### 支出

计入总花费和分类花费：

```javascript
actualCost += amount
categoryCost += amount
```

### 退款

减少总花费和分类花费：

```javascript
actualCost -= amount
categoryCost -= amount
```

### 入账

入账不应简单等同于退款，需要根据业务定义处理。

建议本版本定义为：

- 如果是“退款”，表示对某一类消费的抵扣，应减少对应分类花费。
- 如果是“入账”，表示旅行资金增加，例如成员预存、补贴、返现等，不直接减少消费本身。
- 预算消耗统计默认只看实际消费净额：支出 - 退款。
- 入账可以单独展示为“旅行资金收入”，不参与“已花费”计算。

因此预算统计推荐：

```javascript
netExpense = expenseTotal - refundTotal
availableFund = incomeTotal
```

展示时可以显示：

```text
实际花费：¥3,250
旅行入账：¥500
预算：¥4,000
预算使用率：81.25%
```

如果当前项目暂时不想复杂化，也可以先把 `income` 不纳入预算消耗，只在账单流水中展示。

------

## 8.7 总预算使用率

计算：

```javascript
budgetUsageRate = netExpense / totalBudget
```

示例：

```text
当前总花费 ¥3,250 / 预算 ¥4,000
已使用 81.25%
```

如果没有设置总预算：

```text
当前总花费 ¥3,250
暂未设置预算
```

------

## 8.8 分类预算使用率

每个分类显示：

```text
餐饮 ¥860 / ¥1,200    71.67%
交通 ¥450 / ¥800      56.25%
住宿 ¥1,600 / ¥1,500  106.67% 超预算
```

分类计算：

```javascript
categoryUsageRate = categoryNetExpense / categoryBudget
```

如果分类预算为 0 或未设置：

```text
购物 ¥230
未设置分类预算
```

------

## 8.9 人均预算消耗

人均已花费：

```javascript
perPersonCost = netExpense / activeMemberCount
```

其中 `activeMemberCount` 应使用当前旅行成员数量。

展示：

```text
人均已花费 ¥812.50
```

如果需要考虑已退出成员：

- 账单结算仍按账单参与人计算。
- 预算总览的人均预算消耗默认按当前成员数计算。
- 后续可以扩展为“按参与过账单的成员数”或“按预算成员数”。

V3.0 建议先使用当前旅行成员数量，避免复杂度过高。

------

## 8.10 超预算提醒


```text

```

### 分类预算超出

当：

```javascript

```

显示：

```text

```

# 15. 验收标准

## 15.1 地图选址验收

- 添加行程时可以呼出地图选址。
- 选择地点后能正确回填地点名称和地址。
- 数据库中能保存 latitude 和 longitude。
- 编辑行程时可以重新选择地点。
- 旧行程没有经纬度时页面不崩溃。

------

## 15.2 行程全览验收

- 同一天多个地点可以在地图上展示。
- marker 编号与行程列表编号一致。
- 至少能用 polyline 按顺序连接地点。
- 缺少经纬度的行程会被跳过并提示。
- 当天不足两个有效地点时有合理提示。

------

## 15.3 行程序号验收

- 每天编号从 1 开始。
- 同一天内按开始时间排序编号。
- 第二天重新从 1 开始。
- 普通列表和时间线视图编号一致。
- 地图 marker 编号一致。

------

## 15.4 卡片布局验收

- 行程标题在左侧。
- 时间显示在右侧。
- 地点和备注正常显示。
- 卡片右侧空白明显减少。
- 小屏手机下不发生严重换行错乱。

------

## 15.5 时间线验收

- 可以在列表视图和时间线视图之间切换。
- 时间线按日期分组。
- 时间线按开始时间排序。
- 已结束行程变灰。
- 正在进行或即将进行的行程高亮。
- 点击时间线 item 可以进入详情或编辑。

------

## 15.6 冲突检测验收

- 同一天时间重叠的行程能检测出来。
- 冲突行程卡片显示提示。
- 保存冲突行程时弹窗提醒。
- 用户可以选择取消或仍然保存。
- 没有结束时间的行程不会导致错误判断。

------

## 15.7 预算管理验收

- 可以设置总预算。
- 可以设置分类预算。
- 账单页显示总花费 / 总预算。
- 显示预算使用百分比。
- 超预算时显示超出金额。
- 分类预算显示分类使用情况。
- 退款会减少总花费和分类花费。
- 入账不会错误增加总花费。
- 删除或编辑账单后预算统计同步变化。
- 普通成员不能修改预算。

# 16. Claude Code 开发要求

请严格按照以下要求开发：

1. 不要破坏现有 V2.3 功能。
2. 修改前先理解现有数据结构和页面结构。
3. 所有新增需求文档放入 `spec/` 文件夹。
4. 必须更新 `CHANGELOG.md`。
5. 所有新增工具函数应放入 `utils/` 下，避免页面 JS 过度臃肿。
6. 地图相关逻辑独立封装，不要散落在页面中。
7. 预算计算逻辑独立封装，不要直接写死在账单页面。
8. 行程排序、分组、编号、状态判断、冲突检测应独立封装。
9. 注意兼容旧数据。
10. 注意云开发数据库字段缺失时的容错。
11. 不要伪造路线距离和时间。如果当前接口无法获取准确路线距离和耗时，应明确显示“暂未计算”。
12. 保持微信小程序端 UI 简洁，不要一次性堆叠过多信息。
13. 所有金额统一保留两位小数。
14. 金额输入仍应限制为非负数和最多两位小数。
15. 退款金额在账单展示中建议使用红色或特殊标识，并且必须减少预算消耗。
16. 入账金额应与支出、退款区分展示，不能错误计入总花费。
17. 所有涉及权限的编辑、删除、预算设置入口，都必须在前端显示和后端逻辑中同时校验。

# 18. 最终目标

完成 V3.0 后，「同行旅」应具备以下能力：

1. 用户可以通过地图准确选择行程地点。
2. 用户可以按天查看路线地图，理解当天出行顺序。
3. 行程列表不再只是简单文本，而是有编号、有状态、有时间线。
4. 当前、即将开始、已结束的行程能被直观区分。
5. 时间冲突能被及时提示，但不强制阻止用户保存。
6. 账单模块不只是记录消费，还能帮助用户控制预算。
7. 总预算、分类预算、人均消耗、超预算提醒构成完整预算管理闭环。

V3.0 的核心不是单独增加几个按钮，而是把“行程”和“账单”两个核心模块都提升到更接近真实旅行协作的使用场景。
